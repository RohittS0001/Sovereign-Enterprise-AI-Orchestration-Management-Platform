# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Sovereign (self-hosted, local-LLM) enterprise agentic AI platform for project/delivery management.
FastAPI backend in `backend/app`; an agent answers questions by calling tools over Jira and Gmail,
with human approval for writes, RBAC, and a tamper-evident audit log.

Work proceeds in phases, one local commit each (never push unless asked):
done — 1 foundation, 2 database/auth/RBAC, 3 LangGraph agent + approvals + audit + guardrails.
Planned — 4 GitHub + Keka integrations and Gmail drafting, 5 RAG (pgvector, hybrid search, citations,
permission-aware), 6 org features (project risk score, workload/capacity, forecasts, scheduled reports,
Jira-vs-GitHub contradiction checks, usage tracking), 7 React+TS (Vite) frontend incl. streamed agent
steps, 8 evaluation (DeepEval/Ragas, red-team, CI gates) + observability, 9 Docker Compose, GitHub
Actions, docs. Empty `__init__.py` packages (`retrieval/`, `analytics/`, `reasoning/`, `knowledge/`,
`workflows/`, `evaluation/`) are placeholders for those phases.

## Commands

Windows machine; the Bash tool is Git Bash. Use the venv interpreter explicitly.

```bash
.venv/Scripts/python.exe -m pytest -q                                   # all tests (~15s)
.venv/Scripts/python.exe -m pytest tests/unit/core/test_security.py -q  # one file
.venv/Scripts/python.exe -m pytest "tests/integration/api/test_auth.py::test_refresh_rotates_tokens" -q
.venv/Scripts/python.exe -m pytest --run-live -m live                   # real Jira etc. (skipped by default)
.venv/Scripts/ruff.exe check .        # lint (must pass)
.venv/Scripts/ruff.exe format .       # format
.venv/Scripts/python.exe -m uvicorn backend.app.main:app --reload
.venv/Scripts/python.exe -m alembic upgrade head
.venv/Scripts/python.exe -m alembic revision --autogenerate --rev-id 0003 -m "describe change"
.venv/Scripts/python.exe -m scripts.create_admin --email you@example.com --name "Name"  # ADMIN_PASSWORD env or prompt
.venv/Scripts/python.exe -m scripts.gmail_auth   # one-time interactive Gmail consent -> token.json
```

- Run Alembic as `python -m alembic` (invoking `alembic.exe` directly is denied). Target a scratch DB
  with `-x url=sqlite:///path/to.db`. `tests/integration/test_database.py` runs `alembic check`, so every
  model change needs a migration (hand-tune autogenerated ones, e.g. data seeds).
- Exact pins live in `requirements.txt`; ranges in `pyproject.toml` — update both when adding deps.

## Architecture

**App factory.** `backend/app/main.py:create_app(settings, database, *, agent_models, tool_registry)`
builds everything and stores it on `app.state` (settings, database, rate_limiter, agent_models,
tool_registry). Routes get them through `Annotated` dependencies in `backend/app/api/deps.py`
(`SessionDep`, `SettingsDep`, `PrincipalDep`, `require_permissions(...)`, …). Injected resources are not
disposed on shutdown; only ones the factory created are.

**Request pipeline.** `RequestContextMiddleware` (outermost) sets the request-ID contextvar
(`core/context.py`), writes the access log, and turns unhandled exceptions into a 500 that still carries
the ID → `SecurityHeadersMiddleware` → CORS → routers. Raise `AppException` subclasses from
`core/exceptions/exceptions.py` (not `HTTPException`); handlers render
`{"error": {code, message, details, request_id}}`. Logs are JSON via `core/logging/logger.py`.

**Auth & permissions** (`core/security/`). Short-lived JWT access tokens + opaque refresh tokens
stored hashed and rotated on each use (replay revokes all of the user's sessions). Permissions are
derived from the user's *current DB role* on every request (`Role` → `ROLE_PERMISSIONS`). The agent acts
as `principal.as_agent()` = user permissions ∩ `AGENT_SCOPES`; it can never approve, manage users or read
audit. `APPROVAL_REQUIRED` marks agent writes that need a human.

**Agent run** (`POST /api/v1/agent/query`). `services/agent_service.py` creates an `AgentRun`, then
streams the LangGraph graph in `orchestration/graph.py`:
`plan` (LLM 1, `orchestration/planner/planner.py`, structured output via `llm/structured.py:
generate_structured` → `PlannerOutput`) → `execute` (`orchestration/execution/executor.py`) → back to
`plan` until done or budget hit → `verify` (deterministic) → `respond` (LLM 2,
`agents/reporting/generation/responder.py`, citations `[S1]` filtered to successful steps). Prompts live
in `agents/*/prompts/`. Step ids `S1..` are global across iterations. Tool results are compacted
(`orchestration/observations.py`: drops noisy Jira/Google keys, flattens ADF), redacted, truncated,
injection-scanned, and wrapped in `<untrusted_data>` before any model sees them.

**Tool layering — follow this chain for any new integration (Phase 4: GitHub, Keka):**
1. `integrations/<x>/client.py` — HTTP only; map failures to `IntegrationError(integration=, upstream_status=)`;
   accept an injectable `transport` for tests.
2. `integrations/<x>/service.py` — business operations; validate identifiers used in URLs/queries
   (see `integrations/jira/validators.py`); build the client lazily so construction never needs config.
3. `mcp/schemas/<x>.py` — Pydantic input models (these become the JSON schema shown to the planner).
4. `mcp/tools/<x>.py` — validate input, call service, **return `ToolResult`, never raise**; set
   `retryable=True` for timeouts/429/5xx. Run blocking SDKs via `asyncio.to_thread` (see Gmail).
5. `mcp/catalog.py` — register as `<integration>.<operation>` with description, `input_model`,
   `ToolOperation.READ|WRITE`, and a `Permission`; only when `settings.<x>_configured`.
6. `mcp/registry/tool_registry.py` handles validation, timeouts and read-only retries;
   `orchestration/tool_gateway.py` enforces permission → validation → approval (agent writes become
   `ApprovalRequest`s) → execution, audits every outcome, and commits after each call.

**Approvals** (`services/approval_service.py`, `/api/v1/approvals`). Approving executes the stored call
through the registry and records the result; the run is marked completed once no approval is pending
(the agent is not re-run). Approver needs `approvals:decide` *and* the action's own permission; optional
four-eyes (`APPROVAL_ALLOW_SELF_APPROVAL=false`), TTL expiry, `APPROVAL_EXEMPT_TOOLS` (ignored once a run
is flagged for prompt injection).

**Audit log** (`audit/service.py`). `AuditService(session).record(...)` appends a SHA-256 hash-chained
event *in the caller's transaction* after locking the single `audit_chain_head` row — commit promptly
and never record before a slow call. Action names are constants in `audit/actions.py`; details are
auto-redacted. Never update/delete `audit_events` rows; `/api/v1/audit/verify` detects edits, gaps and
tail truncation.

**Guardrails** (`guardrails/`). `redact_text`/`redact_data` always mask secrets, tokens, card numbers
(Luhn), Aadhaar, PAN, SSN, IBAN; contact info only with `GUARDRAILS_REDACT_CONTACT_INFO`.
`scan_for_injection` is heuristic; a hit adds the `possible_prompt_injection` risk flag to the run.

**LLMs** (`llm/`). `LLMClient` protocol; `OllamaClient` (`/api/chat`, `format`=JSON schema) and
`OpenAICompatibleClient` (`/v1/chat/completions`, vLLM etc.); `AgentModels(operations, reporting)` built
by `llm/factory.py` (LLM 2 falls back to LLM 1). No `LLM1_MODEL_NAME` → agent endpoints return 503.

**Database** (`db/`). Async SQLAlchemy 2; PostgreSQL in prod (psycopg), SQLite in tests — keep types
portable (`Uuid`, `JSON`, `DateTime(timezone=True)` via `Base.type_annotation_map`). SQLite returns
naive datetimes: compare with `as_utc(...)`, create with `utcnow()`. Enums are non-native strings with
`values_callable`. New models must be imported in `db/models/__init__.py`. `normalize_database_url`
swaps only the scheme to async drivers. Settings: single `Settings` in `core/config/settings.py`
(`get_settings()` cached; integration clients default to the module-level `settings`).

## Testing conventions

- `asyncio_mode = "auto"`, `--import-mode=importlib`; import helpers as `from tests.conftest import ...`.
- Key fixtures (`tests/conftest.py`): `test_settings` (ignores `.env`, in-memory SQLite, fixed JWT
  secret), `database` (fresh schema per test), `client` (httpx `AsyncClient` over `ASGITransport`, lifespan
  run by `serve(app)`), `make_user(role=...)`, `auth_headers(user)`, `TEST_PASSWORD`. Build custom apps
  with `create_app(settings, database, agent_models=..., tool_registry=...)` inside `async with serve(app)`.
  Don't use FastAPI `TestClient` (separate event loop from the DB fixtures).
- Agent tests: `tests/support/agent.py` gives the real tool catalog over mocked Jira/Gmail services plus
  scripted `FakeLLM`s (`models([plan(...), DONE], ["answer [S1]"])`).
- Use `example.com` emails in tests; `email-validator` rejects reserved TLDs such as `.test`/`.local`.
- Ruff runs the bandit `S` rules: string constants that merely look like secrets need `# noqa: S105`.

## Environment cautions

- Repo root holds gitignored `.env`, `credentials.json` and `token.json` with the user's **real** Gmail
  OAuth token and Jira credentials (`.env` has a placeholder Jira URL). Don't read them, and never let
  tests, scripts or smoke runs reach real services: for end-to-end checks override `JIRA_*`,
  `GMAIL_TOKEN_FILE`, and `GMAIL_CLIENT_*`, and point `LLM_BASE_URL`/`JIRA_BASE_URL` at local stand-ins.
- No Docker, PostgreSQL or Ollama is installed on this machine; Postgres is verified only via
  `alembic upgrade head --sql` against a `postgresql://` URL. `docker-compose.yml` defines a pgvector DB.
